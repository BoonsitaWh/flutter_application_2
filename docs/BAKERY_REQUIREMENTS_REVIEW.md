# Wongherm Bakery — requirements review

ขอบเขตของโปรเจ็กต์นี้คือแอปพรีออเดอร์ขนมโฮมเมด/เบเกอรี่ เอกสารนี้เทียบฟีเจอร์ที่มีในโค้ดกับโจทย์ Week 2–6 และรายการร้านค้า

## ฟีเจอร์ร้านเบเกอรี่

| ความต้องการ | สถานะในโปรเจ็กต์ | งานที่ยังขาด/ข้อจำกัด |
|---|---|---|
| สมัคร/ล็อกอิน/แก้ไขโปรไฟล์ | มี Supabase Auth, สมัคร/ล็อกอิน/รีเซ็ตรหัสผ่าน และแก้ไข metadata โปรไฟล์ | ต้องตรวจยืนยัน flow กับ Supabase จริงและ RLS; ยังไม่มีระบบยืนยันตัวตนเพิ่มเติม |
| เลือกสินค้า ใส่ตะกร้า และสั่งซื้อ | มี catalog, รายละเอียด, ตัวเลือกสินค้า, ตะกร้า และสร้าง order | การสร้าง order กับ order_items ทำหลาย request แยกกัน จึงควรย้ายไป RPC/transaction เพื่อป้องกันออเดอร์ค้างครึ่งทาง |
| ชำระเงินและยืนยัน | ลูกค้าอัปโหลดสลิปและสถานะรอตรวจ | ยังไม่มี payment gateway/ยืนยันยอดอัตโนมัติ และยังไม่มีหน้าเจ้าของร้านตรวจสลิป/อนุมัติการชำระเงินครบวงจร |
| เจ้าของร้านจัดการสินค้า | เพิ่ม/แก้ไข/soft-delete สินค้า, อัปโหลดหลายรูป, ตัวเลือกข้อความอิสระ | ตัวเลือกยังไม่มีโครงสร้างสี/ขนาดและราคา/สต๊อกแยกตัวเลือก; ต้องใช้ RLS ควบคู่กับการซ่อนปุ่มใน UI |
| Dashboard เจ้าของร้าน | มีหน้าเริ่มต้นพร้อมทางไปจัดการสินค้า แชท และคำสั่งซื้อ; เพิ่มรายการออเดอร์ กรองสถานะ ตรวจสลิป และอัปเดตสถานะแล้ว | ยังไม่มีสรุปยอดขาย/ตัวชี้วัด; ต้อง apply migration และ RLS/Storage policies บน Supabase จริงก่อนตรวจสลิปได้ |
| รายการสินค้า/ค้นหา/กรอง | มี grid, ค้นหาชื่อ/รายละเอียด และกรองหมวดหมู่ | ไม่มี sort/filter ราคาและตัวเลือก; ต้องทดสอบกับข้อมูลจริงและหมวดหมู่ที่ตั้งใน backend |
| แชทลูกค้ากับร้าน | มีแชทข้อความแบบ realtime ลูกค้า↔เจ้าของร้าน | ยังส่งรูปในแชทไม่ได้; ต้อง apply migration และตรวจ RLS/Realtime บน Supabase |
| คูปอง/ส่วนลด | ยังไม่มี | ต้องทำ validation และคำนวณยอดฝั่ง server ก่อนแสดงยอดสุทธิ |
| ประวัติคำสั่งซื้อ | มีหน้าประวัติ/รายละเอียดออเดอร์ | ควรเพิ่มสถานะเตรียม/พร้อมรับ/จัดส่ง/ยกเลิก และจัดการโดยเจ้าของร้าน |
| สต๊อก | มีช่องกรอกและแสดงสต๊อก (หลังใช้ migration) | ยังไม่ reserve/decrement แบบ atomic ตอน checkout; ห้ามถือเป็นยอดคงเหลือเชื่อถือได้เมื่อมีลูกค้าสั่งพร้อมกัน |
| แจ้งเตือน | มีแจ้งเตือนในแอป | ยังไม่มี push notification |
| ฟีเจอร์จาก pain point | มี search, order history, payment proof และ support chat | ควรเก็บ feedback จริงเรื่องวันรับสินค้า/รอบรับ, สั่งล่วงหน้า, สินค้าหมด, แพ้อาหาร/ส่วนผสม, ยกเลิกหรือเลื่อนรับ ก่อนจัดลำดับฟีเจอร์ใหม่ |
| Cloud database | ใช้ Supabase | repository มี migration เฉพาะ chat และ stock ไม่ได้มี schema/bootstrap/RLS ครบทุกตาราง; ต้องเทียบกับ project จริงก่อน deploy |

## เทียบแผน Week 2–6

| สัปดาห์ | มีแล้ว | สิ่งที่ควรเติม |
|---|---|---|
| Week 2 — UX/UI | ปัญหา/กลุ่มผู้ใช้, flow ลูกค้าและร้าน, wireframe 5 หน้าจอ, โครงสร้างโปรเจ็กต์และธีมใน `docs/PROJECT_BRIEF.md` | ขอ feedback จากลูกค้า/เจ้าของร้านจริงและบันทึกการปรับ wireframe |
| Week 3 — Vertical slice & data | Auth, CRUD สินค้า, SQLite read cache, data model และ error handling | ทำ checkout/order creation เป็น transaction, จัด schema/RLS migration ให้ครบ, พิจารณา offline write queue หาก rubric ต้องการ sync สองทาง |
| Week 4 — Integrations | chat ข้อความ, in-app notification, upload รูปสินค้า, search/filter | ส่งรูปในแชท, push notification และทดสอบ integrations กับ Supabase จริง |
| Week 5 — Polish & test | 18 unit tests (ตะกร้า 12 + cache 6), accessibility บางส่วน, manual acceptance cases | เพิ่ม integration/UI tests สำหรับ auth, order, payment proof, owner review, stock; ตรวจ TalkBack/VoiceOver, text scale และอุปกรณ์จริง |
| Week 6 — Final delivery | README, demo flow, Android APK ที่บันทึกไว้ | สร้าง APK จาก source ล่าสุด, ติดตั้งทดสอบบนอุปกรณ์, ตรวจ GitHub push; TestFlight ทำได้เมื่อมี iOS target และ signing เท่านั้น |

## ลำดับงานที่แนะนำ

1. เพิ่มสรุปยอดขายและตัวชี้วัดรายวัน/รายเดือนใน owner dashboard
2. ทำ checkout แบบ transaction พร้อมตรวจและตัดสต๊อกฝั่ง server
3. เพิ่มวัน/รอบรับสินค้าและ validation ระยะเวลาพรีออเดอร์
4. ทำตัวเลือกสินค้าแบบมีโครงสร้าง (เช่น ขนาด/รสชาติ) และราคา/จำนวนต่อ option
5. เพิ่มคูปองโดยคำนวณ/ตรวจสิทธิ์ที่ server
6. เพิ่มรูปในแชทและ push notifications
7. ทดสอบกับผู้ใช้จริงเรื่องส่วนผสม/สารก่อภูมิแพ้ การเลื่อนรับ การยกเลิก และสินค้าหมด แล้วจัดลำดับตาม pain point ที่พบ

## ขอบเขตการทดสอบปัจจุบัน

มี automated unit tests 18 เคสสำหรับตะกร้าและ SQLite cache เท่านั้น ยังไม่ครอบคลุม flow ที่พึ่ง Supabase จริง เช่น สมัคร/ล็อกอิน, RLS, สร้างออเดอร์, อัปโหลดและตรวจสลิป, การลดสต๊อก, แชท และการแจ้งเตือน ส่วน acceptance cases ใน `TEST_PLAN.md` เป็นรายการทดสอบมือที่ต้องทำกับ backend/device จริง
